## 0. 总则的落地口径 `[实测]`

### 0.1 「进阶 10 的数值」在代码里怎么写

`AscensionLevel` 的枚举顺序就是档位：

```
None=0, SwarmingElites=1, WearyTraveler=2, Poverty=3, TightBelt=4,
AscendersBane=5, Inflation=6, Scarcity=7, ToughEnemies=8, DeadlyEnemies=9, DoubleBoss=10
```

`AscensionManager.HasLevel(level) => 当前等级 >= (int)level` —— 所以**在进阶 10，所有档位都生效**，包括 `ToughEnemies`(8) 与 `DeadlyEnemies`(9)。

因此代码写法是：**你给的数值放「进阶值」位，低进阶值放 fallback 位**：

```csharp
// 例：明萨拉
public override int MinInitialHp => AscensionHelper.GetValueIfAscension(AscensionLevel.ToughEnemies, 150, 142);
public override int MaxInitialHp => MinInitialHp;
private int Attack20Damage => AscensionHelper.GetValueIfAscension(AscensionLevel.DeadlyEnemies, 20, 17);
```

### 0.2 多人数值：**不需要你算，引擎自动做** `[实测]`

- **血量**：`Creature.ScaleMonsterHpForMultiplayer()` = `MaxHp × 玩家数 × MultiplayerScalingModel.GetMultiplayerScaling(encounter, actIndex)`，在 `CombatState.CreateCreature` 里自动调用。
- **能力层数**：`PowerModel.ShouldScaleInMultiplayer => true` 时，`PowerCmd.Apply` 会自动把 Amount 按玩家数缩放（原版 `RampartPower` 就是这么做的）。
- **敌人格挡**：`MultiplayerScalingModel.ModifyBlockMultiplicative` 会自动缩放"有来源的敌方格挡"。

→ **结论：mod 只需要写单人 A10 的基准值**，多人由引擎按原版规则缩放。设计稿里"多人数值按原版比例算出来"这条**不需要人工计算**，只要把 `ShouldScaleInMultiplayer` 标对即可。

### 0.3 低进阶数值的推导规则 `[默认]`

原版没有统一公式（逐怪手调），实测统计结果：

| 项目 | 样本 | 比例中位数 | 分布 |
|---|---|---|---|
| 血量（ToughEnemies） | 60 组 | **×1.056** | 1.019 ~ 1.150 |
| 伤害（DeadlyEnemies） | 50 组 | **×1.148** | 1.000 ~ 3.000（小数值抖动大） |

**我采用的默认换算**（`低进阶值 = round(A10值 ÷ 比例)`）：

- 血量：`A10 ÷ 1.06`
- 伤害：`A10 ÷ 1.15`，最小 1（小数值常常除完不变，原版也是这样，如 Byrdonis 3→3）

### 0.4 伪代码的执行口径（按你写的 C++ 语义）`[原稿]`

- **有实际动作的语句 = 1 个敌方回合**（攻击 / 强化 / 自己眩晕 / 上灵光）
- **纯逻辑语句（if / while / for / break）不占回合**，在它出现的位置**瞬时求值**
- `for i in range(2)` 是编译期常量 → **展开成 8 个动作**（编译器就是这么做的）
- 被动眩晕（玩家晕它）→ 顺延一回合

> ⚠️ **这条口径会产生一个重要的语义后果，见 4.3。**

### 0.5 幕归属 `[原稿]`

第一/二/三层都可塞，不区分 Overgrowth / Underdocks。落成代码即：

```csharp
public override bool IsValidForAct(ActModel act) => act.Index is >= 0 and <= 2;   // 第一、二、三层
```

> 注意 `act.ActNumber()` 会返回 1/2/3，但 Overgrowth 与 Underdocks 的 `Index` 都是 0，所以 `ActNumber()==1` 同时命中两个第一幕 —— 用 `Index` 判断即可，不需要区分。

## 4. D2 · 意图状态机表

### 4.1 地精·近战 `GoblinMelee`

原稿：`攻击2*1 → 攻击3*1 → 强化1力量 → 攻击2*1 → 攻击3*1 → 强化1力量 → while{ 攻击2*1; 攻击3*1 }`

展开后的线性链（8 个节点，无循环状态）：

| # | MoveState ID | 意图 | 效果 | FollowUp |
|---|---|---|---|---|
| 1 | `HACK` | `SingleAttackIntent(2)` | 造成 2(2) 点伤害 | → 2 |
| 2 | `JAB` | `SingleAttackIntent(3)` | 造成 3(3) 点伤害 | → 3 |
| 3 | `RALLY` | `BuffIntent` | 自身 +1 力量 | → 4 |
| 4 | `HACK2` | 同 `HACK` | 造成 2 点伤害 | → 5 |
| 5 | `JAB2` | 同 `JAB` | 造成 3 点伤害 | → 6 |
| 6 | `RALLY2` | 同 `RALLY` | 自身 +1 力量 | → 7 |
| 7 | `HACK_LOOP` | 同 `HACK` | 造成 2 点伤害 | → 8 |
| 8 | `JAB_LOOP` | 同 `JAB` | 造成 3 点伤害 | → 7 |

- 招式名（`moves.<ID>.title`）：`HACK`=劈砍、`JAB`=突刺、`RALLY`=战吼、`HACK_LOOP`/`JAB_LOOP` 复用同名前缀 **`[默认]`**
- **`2`/`3`/`4` 结尾的 ID 若不给 loc，引擎会自动从图鉴里静默跳过**（`MonsterModel.GenerateBestiaryMoveList` 的既有约定）→ 所以 `HACK2`/`JAB2`/`RALLY2` **不要写 loc**，图鉴里就只显示 3 个招式，不会重复。`[实测]`
- ⚠️ 攻击值 2 / 3 在低进阶下**不变**（`round(2/1.15)=2`、`round(3/1.15)=3`），即这只怪**完全不吃 `DeadlyEnemies` 进阶加成**。若希望它随进阶变强，A10 值需要提到 4 以上（`4→3` 才会产生差值）。`[默认，可推翻]`

### 4.2 地精·远程 `GoblinRanged`

原稿：`while{ 攻击2*1; 自己眩晕; 强化1力量 }`

| # | MoveState ID | 意图 | 效果 | FollowUp |
|---|---|---|---|---|
| 1 | `SHOOT` | `SingleAttackIntent(2)` | 造成 2(2) 点伤害 | → 2 |
| 2 | `RELOAD` | `StunIntent` | **自己**这回合不行动 | → 3 |
| 3 | `RALLY` | `BuffIntent` | 自身 +1 力量 | → 1 |

- 「自己眩晕」的实现：一个 `MoveState`，`onPerform` 为空、意图用 `StunIntent`。**不是** `CreatureCmd.Stun`（那是给"被外部眩晕"用的）。`[实测]`
- 三招循环 → 它每 3 回合只打 2 点，配 30 血，是全场最弱的输出源。

### 4.3 油桶 `OilBarrel`

| # | MoveState ID | 意图 | 效果 | FollowUp |
|---|---|---|---|---|
| 1 | `IDLE` | `StunIntent` | 永远不行动 | → 1（自循环）|

### 4.4 明萨拉 `Minthara`

原稿：

```
while(true) {
    for i in range(2) { 强化:守护灵光; 强化:勇气灵光; 攻击8*1; 强化获得2力量; }
    攻击20*1;
    if (两个地精队友都死了) break;
}
while (true) { 攻击20*1; 强化获得1力量; }
```

展开后的完整状态链：

| # | MoveState ID | 意图 | 效果 | FollowUp |
|---|---|---|---|---|
| 1 | `AURA_GUARD` | `BuffIntent` | 给全体友方上「守护灵光」 | → 2 |
| 2 | `AURA_VALOR` | `BuffIntent` | 给全体友方上「勇气灵光」 | → 3 |
| 3 | `SLAM` | `SingleAttackIntent(8)` | 造成 8(7) 点伤害 | → 4 |
| 4 | `RALLY` | `BuffIntent` | 自身 +2 力量 | → 5 |
| 5 | `AURA_GUARD2` | 同 1 | 同上 | → 6 |
| 6 | `AURA_VALOR2` | 同 2 | 同上 | → 7 |
| 7 | `SLAM2` | 同 3 | 造成 8(7) 点伤害 | → 8 |
| 8 | `RALLY2` | 同 4 | 自身 +2 力量 | → 9 |
| 9 | `SLAM_BIG` | `SingleAttackIntent(20)` | 造成 20(17) 点伤害 | → 10 |
| 10 | `PHASE_CHECK` | `ConditionalBranchState`（不出现在图鉴/日志） | 见下 | → 11 或 → 1 |
| 11 | `SLAM_LOOP` | `SingleAttackIntent(20)` | 造成 20(17) 点伤害 | → 12 |
| 12 | `RALLY_LOOP` | `BuffIntent` | 自身 +1 力量 | → 11 |

`PHASE_CHECK` 的判定（`ConditionalBranchState`，**按添加顺序取第一个成立的分支**）：

```
分支 1: → SLAM_LOOP    条件 = 地精·近战 与 地精·远程 均已阵亡
分支 2: → AURA_GUARD   条件 = () => true   （兜底，永真）
```

- `9` 与 `11` 是**两个不同的状态**，因为 `FollowUpState` 是每个状态各自的属性。虽然效果相同（都是 20 点），ID 必须分开。`[默认]`

**「两个地精队友都死了」的判定** `[默认]`：

```csharp
private bool BothGoblinsDead() =>
    CombatState.Enemies.Where(c => c.Monster is GoblinMelee or GoblinRanged).All(c => c.IsDead);
```

- **油桶不算队友** —— 你新加的「爪牙」(`MinionPower`) 正好在引擎层把它标成了 `IsSecondaryEnemy`（"次要敌人"），语义完全吻合。`[实测]`
- 原版可抄的写法：`RampartPower.cs:27` 用 `CombatState.Enemies.Where(c => c.Monster is TurretOperator)` 判特定队友存活。
- ⚠️ 用 `.All(...)` 前要确认集合非空（若地精还没生成完毕会得到 `true`）；建议先 `.Any()` 再 `.All()`。

#### ⚠️ 语义后果：这条 `break` 会让第一阶段**最少走满 9 招**

按你定的 C++ 语义，`if` 只在它出现的位置求值一次 —— 也就是**每轮 while 只在第 9 招（`SLAM_BIG`）之后查一次**。后果：

1. **玩家即使第 1 回合就清掉两个地精，明萨拉仍会完整走完 9 招的第一阶段**，第 10 个敌方回合才进第二阶段。
2. **转阶段时会连打两个 `攻击20`**：第 9 招（`SLAM_BIG`）判定成立后 break，立刻进入第二个 while 的第 1 招（`SLAM_LOOP`），也是 20 点。
3. **这 9 招内的输出**：`SLAM 8` + `SLAM2 8` + `SLAM_BIG 20` = **36 点**，外加 `RALLY`×2 = **+4 力量**（之后所有攻击都带这个加成）。
4. 加上地精（近战 9 招内约 17 点、远程约 6 点），**第一阶段玩家就要吃 ~59 点伤害**。
5. 她自身 150 血，玩家第一幕的输出能力大约 15–25/回合 → 打完她要 7–10 个回合，而这期间她的攻击是 20 起、每 2 回合 +1。

**→ 按字面语义，这场精英战在第一幕大概率打不过。**

如果你的原意是"小怪死 → 立刻转阶段"，那 `break` 需要改成**每次行动后都判一次**（把 `PHASE_CHECK` 插在 `RALLY` 之后而不是只插在 `SLAM_BIG` 之后，或者做成"每回合开始前先判一次"）。这属于**语义澄清**而非信息缺失，我按你给的 C++ 口径实现字面版本，改动方式记在此处备选。

### 5.2 5 只怪：**不是引擎上限，只是布局调优** `[实测·已证伪初稿结论]`

> ⚠️ **修订**：初稿写的"原版全部遭遇最多 4 只怪、5 只超上限"**是错的**。源码实查如下。

`EncounterModel.Slots` 只是场景里 `Marker2D` 的名字列表，数量无上限；且**同时存活敌人数可以超过槽位数**（靠动态召唤）：

| 出处 | 槽位 | 同时存活敌人 | 镜头 |
|---|---|---|---|
| **`PhrogParasiteElite`**（第一幕精英） | 5 | 本体 1 → 死后 `InfestedPower.AfterDeath` 招 **4 只 Wriggler** = **5 只** | `0.95` |

#### 修正 1：必须挂在 `AfterDeath`，不能挂 `BeforeDeath` `[实测]`

`AbstractModel.BeforeDeath` 的源码注释原文：

> *"Runs before a creature dies. **Note: This will run even if some effect (like Fairy in a Bottle) would prevent the creature's death.**"*

→ 挂 `BeforeDeath` 会导致**死亡被防住时也照样炸**。正确做法是 `AfterDeath`，它提供 `wasRemovalPrevented` 参数专门用于此判断。

原版有**现成的同构模板** —— `Core/Models/Powers/InfestedPower.cs`（PhrogParasite 死后招 4 只 Wriggler）：

```csharp
public override async Task AfterDeath(
    PlayerChoiceContext choiceContext, Creature target,
    bool wasRemovalPrevented, float deathAnimLength)
{
    if (!wasRemovalPrevented && base.Owner == target)
    {
        // 我们的引爆逻辑放这里
    }
}
```

`[默认]` 直接照抄这个签名与守卫。

#### 修正 2：只靠 `IsOverOrEnding` **挡不住**爪牙连带死亡 `[实测]`

初稿建议用 `CombatManager.Instance.IsOverOrEnding` 判断"战斗正在收尾"。查 `CreatureCmd.cs` 的实际顺序后确认**这个判断在这个场景下会失效**：

```
KillWithoutCheckingWinCondition(primaryEnemy)
  → Hook.BeforeDeath → Hook.AfterDeath(primaryEnemy)     ← 此时还没判胜负
  → if (isPrimaryEnemy && teammates.All(t => t.IsSecondaryEnemy)) await Kill(teammates)
        → KillWithoutCheckingWinCondition(油桶A) → 油桶A 的 AfterDeath ← 此时仍未判胜负
```

胜负判定在 `CreatureCmd.Kill(creatures, force)` 的**整个循环之后**才执行（`LoseCombat()` / 结算胜利）。所以在油桶的 `AfterDeath` 里，`IsOverOrEnding` **仍然是 false** → 引爆会照常触发 → 玩家在**已经赢了的瞬间吃 10 点伤害甚至死掉**。

**正确的守卫**（两条件任一成立即跳过）：

```csharp
private bool ShouldSkipExplosion() =>
    CombatManager.Instance.IsOverOrEnding            // 兜底：战斗确实已结束
    || !Owner.CombatState!.Enemies.Any(c => c.IsAlive && c.IsPrimaryEnemy);  // 核心：无存活主要敌人
```

- `Creature.IsPrimaryEnemy` = `Side == Enemy && !IsSecondaryEnemy`；`IsSecondaryEnemy` = 身上有任一 `OwnerIsSecondaryEnemy == true` 的 power → 油桶因「爪牙」(`MinionPower`) 恰好是 `IsSecondaryEnemy`。`[实测]`
- 语义即："**主要敌人全死 → 这场战斗已经赢了，不留遗产**"。比 `IsOverOrEnding` 更早、更可靠。
- `[实测]` `IsAlive => CurrentHp > 0`；`IsDead => !IsAlive`。

**其余两条规则**（设计稿未写，我按保守可玩的方向默认）：

3. **同一条引爆链中，每个油桶只触发一次。** `[默认]`
   `[实测]` 场上有 **2 个**油桶：炸死 A → A 对 B 造成 `5/3 = 1` 点 → 若 B 因此死亡则再次引爆……引擎有递归保护（`KillWithoutCheckingWinCondition` 里 `recursion >= 10` 会抛 `"Combat is ending, but something is continually preventing the last creature from being killed!"`），但报错本身不可接受。
   实现：战斗作用域内维护"本链已引爆集合"，或直接依赖 `MaxHp/3` 对 5 血桶向下取整 = 1、1 点打不死 5 血桶这一**天然安全**的性质（但以后加更多油桶或调低血量就会出问题，仍建议显式加保护）。

4. **被拾取杀死时不触发。** `[原稿]`
   `[实测]` `Hook.BeforeDeath(runState, combatState, creature)` 与 `AbstractModel.BeforeDeath(creature)` **都不带击杀者/来源参数** —— 只能由拾取卡自己打标记。
   实现：拾取卡在 `Kill` 之前先给目标挂一个隐藏标记 power（`BeingPickpocketedPower`），`DeathExplosionPower` 里检查 `Owner.HasPower<BeingPickpocketedPower>()` → 有则直接 return。

### 6.3 「爪牙」`[原稿]` → 直接用原版 `MinionPower` `[实测]`

原版 `Core/Models/Powers/MinionPower.cs` 完全就是你要的东西：

```csharp
public override bool OwnerIsSecondaryEnemy => true;            // 标记为"次要敌人"
public override bool ShouldOwnerDeathTriggerFatal => false;    // 它死了不算战斗失败/胜利判定
public override bool ShouldPowerBeRemovedAfterOwnerDeath => false;
public override bool ShouldPlayVfx => false;                   // 不播 power 图标特效
```

语义（`Creature.cs` 注释原文）：**次要敌人只有在还有活着的"主要敌人"时才存在，否则会自动死亡**。
→ 油桶跟着明萨拉/地精活，主要敌人全灭时自动陪葬。这正是你要的"爪牙"。

**收益**：`IsSecondaryEnemy` 还会让油桶在 `CreatureCmd` 的"主要敌人死亡"分支里被正确处理（自动陪葬），不用自己造轮子。

#### 怎么挂上 `MinionPower` `[实测]`

原版 `GasBomb`（`Core/Models/Monsters/GasBomb.cs`，就是 `LivingFogNormal` 里那些炸弹）的写法可直接照抄：

```csharp
public override async Task AfterAddedToRoom()
{
    await base.AfterAddedToRoom();
    await PowerCmd.Apply<MinionPower>(
        new ThrowingPlayerChoiceContext(), base.Creature, 1m, base.Creature, null);
}
```

→ **挂在 `AfterAddedToRoom`，不是在遭遇里预先施加**。这样动态生成的油桶（若有）也会正确获得爪牙。

> 附带发现：`GasBomb` 是油桶的**结构性模板**（不只是美术占位）——
> 它是"不会主动攻击、被清掉就爆炸"的爆炸物，用 `DeathBlowIntent` 表示"炸"，
> 有 `explode` 动画，且 `ShouldFadeAfterDeath => false`（留尸）。
> `[默认]` 油桶照抄 `ShouldFadeAfterDeath => false` 与 `DamageSfxType.Magic`。

### 6.4 「守护灵光」`GuardAuraPower` `[默认]`

| 项 | 取值 |
|---|---|
| `PowerType` | `Buff` |
| `PowerStackType` | **`Counter`**，Amount = **每回合格挡值 5** |
| `ShouldScaleInMultiplayer` | **`true`** ← 精确复制原版 `RampartPower`，多人自动按人数缩放 |
| 持续回合数 | **放 power 的 internal data（不是 Amount）**，初值 2 |
| 生效时机 | `AfterSideTurnStart(side, participants, combatState)`，`side == CombatSide.Player` 时触发 |
| 目标 | `CombatState.Enemies` 全体的持有者（**含明萨拉自己**）`[原稿]` |
| 给格挡的 props | `ValueProp.Unpowered`（同 `RampartPower`） |
| 递减时机 | `AfterSideTurnEnd(side == CombatSide.Enemy)` 时把 internal data 的回合数 −1；**施加当回合的那一次递减跳过** |
| 图标 | 64×64 + 256×256（后期补，先借原版占位） |

**为什么 Amount 放格挡值而不是回合数** `[默认]`：因为 `ShouldScaleInMultiplayer` 只缩放 `Amount`。把回合数放进 Amount 会导致"多人模式下持续回合数被乘以人数"。原版 `RampartPower` 正是让 Amount 承担数值、并且开了 `ShouldScaleInMultiplayer`。

**"持续2回合"的精确落地**：明萨拉在**敌方回合**上 buff；玩家回合开始给格挡。
- 跳过施加当回合末的递减 → 玩家回合 N+1 给一次、N+2 给一次，共 **2 次**，第 3 次不给。这就是"持续 2 回合"。
- 参考实现：原版 Weak/Frail/Vulnerable 用 `PowerCmd.TickDownDuration` + `SkipNextDurationTick`（`WeakPower.cs:49-55`）。

**叠加规则** `[默认]`：**刷新持续时间、不叠数值**。第一阶段循环两轮会放 2 次灵光，第 2 次只把剩余回合数重置为 2，格挡值仍是 5。（若你想叠加，改成 `Amount += 5` 即可，但一场 5 只怪的战斗里会很膨胀。）

### 6.5 「勇气灵光」`ValorAuraPower` `[默认]`

| 项 | 取值 |
|---|---|

### 7.1 「无色牌」的措辞要改

原稿写「本mod专属**无色牌**」+「只在 catch 战斗中才有」—— 这两条在引擎里是互斥的：

- **进卡池**的牌才能叫"无色牌"（能被抽到、能被奖励、能被商店卖）；
- 你要的是**战斗内动态生成的临时牌**，它**根本不在卡池里**。

`[默认]` 我按后者实现：它是一个 `CardModel` 子类，但**不注册进任何 CardPool**，仅由 `AfterPlayerTurnStart` 逻辑在 catch 战斗中动态生成到手上。所有角色（含 Denia 等 mod 角色）都能用。

> 建议把设计稿里的"无色牌"改成"**本 mod 专属、战斗内生成的临时牌**"，避免后续被误解成要进无色卡池。

### 7.2 其余口径的默认值

| 问题 | 默认取值 | 理由 |
|---|---|---|
| 手牌满（≥ `CardPile.MaxCardsInHand` = 10）时 | **不塞**（静默跳过） | `[实测]` 手牌上限 10，引擎自己的抽牌也是这么截断的 |
| 每场战斗的塞牌上限 | **不设上限** | 油桶只有 2 个，天然收敛；若以后加更多可拾取怪再加 |
| 拾取是否算"击杀"给金币 | **算**（走引擎默认的 `CalculateGoldProportion`） | 不额外处理 = 与原版击杀一致 |
| 拾取是否绕过死亡防止 | **`force: true`** | `[原稿]` "直接令该敌人死亡"是无条件的；`force:false` 会被"死亡防止"类效果挡下导致拾取静默失败 |
| 强制结束回合的时机 | **只要打出这张牌就结束**（无论是否有目标、是否成功） | 与「花费一个动作」的 BG3 语义一致，且规则最简单不易出歧义 |
| 目标选择 | 允许选中任何敌人；选了没「可被拾取」的 = 白打 | 保持与"无效果"的一致性 |

## 11. 仍需你确认的唯一一件事

**4.4 节里那条 `break` 的语义后果**：按你定的 C++ 口径，玩家即使第 1 回合清光小怪，明萨拉仍会走满 9 招的第一阶段、并在转阶段时连打两个 20 点，第一阶段玩家共吃约 59 点伤害 —— 以第一幕精英的强度基准看，这场大概率打不过。

我按**字面口径**实现（因为这是你写进总则的规则），但如果你要的是"小怪死 → 立刻转阶段"，改动很小（把判定从"只在 `SLAM_BIG` 后查"改成"每次行动后都查"）。**这是数值强度问题，不是信息缺失**，所以没有替你决定。
